# Handoff — transferring the project back to another laptop / workspace

Everything needed to run the project after a transfer. Nothing secret is stored
in Git, so the receiving person must recreate two files: `.env` and `backend/.env`.

---

## 1. One command setup

```bash
# macOS / Linux
bash scripts/setup-env.sh

# Windows
scripts\setup-env.bat
```

This creates `.env` and `backend/.env` from the templates, generates a random
`JWT_SECRET`, and creates `backend/uploads/` + `backend/data/`.

Then:

```bash
bash scripts/start.sh      # Windows: scripts\start.bat
```

Frontend: http://localhost:8080 — Backend: http://localhost:5000

---

## 2. Values to fill in by hand

### `backend/.env`

| Variable | Required? | Where it comes from |
|---|---|---|
| `JWT_SECRET` | yes | auto-generated by the setup script |
| `MASTER_ADMIN_ID` / `MASTER_ADMIN_PASSWORD` | yes | choose your own (this is the master admin login) |
| `ADMIN_ID` / `ADMIN_PASSWORD` / `ADMIN_NAME` | yes | choose your own bootstrap admin |
| `CORS_ORIGINS` | yes | `http://localhost:5173,http://localhost:8080` locally; add the published URL in production |
| `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM` | for emails | Gmail account + **App Password** (not the normal password) |
| `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | production only | from the Cloud backend of the workspace that owns the project |
| `LOVABLE_API_KEY` / `GOOGLE_DRIVE_API_KEY` | Drive uploads only | injected automatically when the Google Drive connector is linked |
| `MAX_UPLOAD_MB` | no | defaults to 25 |

### `.env` (frontend)

| Variable | Notes |
|---|---|
| `VITE_API_URL` | `http://localhost:5000` locally; the Railway URL in production |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID` | auto-written by Lovable when Cloud is enabled in that workspace |

---

## 3. Works without any cloud keys

If Supabase / Drive / SMTP values are blank the app still runs:

- Data → JSON files in `backend/data/`
- Uploaded files → `backend/uploads/`
- Face-verification codes → printed in the backend console instead of emailed

Add the cloud keys later without any code change.

---

## 4. Workspace-level things that do NOT transfer with the code

These live in Lovable, not in Git, and must be redone in the new workspace:

1. **Lovable Cloud** — enable it; new Supabase URL/keys are written into `.env`.
2. **Gmail connector** — Connectors → Gmail → connect + link to the project.
3. **Google Drive connector** — Connectors → Google Drive → connect + link.
   Only the project owner can link a connection they have access to.
4. **Published URL / custom domain** — republish from the new workspace.
5. **Railway backend** — redeploy and re-enter the same env vars there
   (see `DEPLOY.md`), then update `VITE_API_URL` and `CORS_ORIGINS`.

---

## 5. Transfer checklist

- [ ] Push latest code to GitHub (Plus menu → GitHub)
- [ ] Friend clones the repo
- [ ] Friend runs `scripts/setup-env.sh` / `.bat`
- [ ] Friend fills the admin + SMTP values in `backend/.env`
- [ ] `bash scripts/start.sh` → app runs locally
- [ ] (Cloud) enable Lovable Cloud + link Gmail and Google Drive connectors
- [ ] (Production) redeploy backend on Railway, set `VITE_API_URL`, republish
